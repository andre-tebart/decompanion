# asmdiff/diffclass misalign a chain of near-identical blocks after a one-register difference

- **Source:** match-base session 2026-11-01 (gildegold), worker 14
- **Severity:** critical (fixed in decompanion 87cebdd)
- **What happened:** in sv_RefreshPanel, moving the `j == 0` block of the job-kind chain to the end (where the original has it) made codegen closer, yet distance went from 339 to 423 differing and diffclass reported large `code` hunks. One register difference in the case-0x61 body (ours `mov ecx, esi`, original `mov edx, esi`) made the aligner skip a whole ~40-line case and pair 0x43 with 0x62, 0x62 with 0x65, etc. `asmdiff --all` shows the original's `cmp cl, 0x43` at 0x529a51 opposite our `cmp cl, 0x43` at 0x529a74 with a full + block before it. After a later unrelated register shift the same function showed 118 differing and 4 code hunks.
- **Expected:** anchor alignment on compare constants and calls, or score a register-renamed instruction as a cheap match before insert/delete.
- **Repro:** at gildegold commit "sv: sv_RefreshPanel -> deep" (before 4dc46a1), replace `d2_WinOpenPicStyledS(` with `d2_WinOpenPicStyled(` in sv_RefreshPanel, then `uv run dcp asmdiff sv_RefreshPanel --all | grep -n "cmp cl, 0x"`.
- **Impact:** 15-20 minutes and a near-wrong revert of a correct change.
- **Related:** diffclass-rotation-with-reorder-as-code.md, ../improvement-reports/asmdiff-regs-auto.md

## Also seen (match-base session 2026-11-02 (gildegold), worker 39) - critical, FIXED in 87cebdd

GNU diff with addresses masked found 645 differing lines, with registers / `[esp+N]` also masked 151. Worker stopped the session as critical (near-shape functions graded draft; no truthful escalation hunk list possible).
- **Root cause:** `src/difflib.rs` was a port of Python's `difflib.SequenceMatcher` (Ratcliff/Obershelp: longest contiguous run first, then recurse), not an LCS. With a block repeated 11 times, the longest run paired ours' k-th copy with a different original copy, leaving whole copies unpaired and `join` merging them into one hunk. Second issue: `join` merges differences < 5 equal lines apart, so even a correct alignment could put two loop copies with different register allocations in one hunk, which no single renaming explains -> `code`.
- **Fix:** (1) difflib replaced by linear-space Myers diff on interned lines (minimal edit script, same opcode shape). (2) diffclass: a joined hunk classified `code` with several differing runs is cut recursively at its widest equal run and each half classified (pieces go to `classify` only if they match as a multiset with registers and `[reg+-N]` masked, or are FPU/fill; new `x86::shape_keys`); consecutive code pieces re-merged; same for the frame-aligned path. 5469812's order_keys untouched.
- **Tests:** difflib vs quadratic LCS on 3000 random pairs; repeated-copies case (both fail on the old matcher); `diffclass::repeated_loops` (11 slot-only copies -> shape; two copies with different registers -> regs pieces; unexplained piece stays code). `cargo test` 189 passed, 35 ignored. With `--include-ignored`, 2 e2e tests (`servers::match_server`, `servers::ghidra_export_and_draft`) fail, also on unmodified HEAD - pre-existing, unrelated (worth a separate look).
- **Timing:** Myers worst case 3000x3000 fully different ~40 ms; cold project-wide grade ~1.0 s -> ~1.3 s; warm diffclass/asmdiff ~80 ms unchanged.
- **Effect on gildegold (1818 non-byte functions):** ai_FillNearRing `differing` 1203 -> 571 (code 377, slots 366, regs 54, branch 33; still draft with real code hunks). Verdicts: draft -> shape 6 (ch_PathToTarget, vfs_EntryPath, d2_BankConvertTo16, ai_CommandCityTreasury, ai_ChooseMission, gv_FireShots), shape -> draft 0. Total differing 250602 -> 231322; 9 functions +2..6 (frame-masked count). Expected at next wrap: +6 shape / -6 draft, no byte changes, no falls.

## Residual after 87cebdd (match-base session 2026-11-02 (gildegold), worker 39) - open, minor
- ai_FillNearRing still pairs one of the 11 loop copies one copy apart: `uv run dcp diffclass ai_FillNearRing --all` at gildegold 3be9fb1 shows 0x004a3f18 `code 61` (58 lines ours, 3 original) and 0x004a4393 `code 67` (2 ours, 65 original): the same loop body seen one copy apart (copies differ only in slots, registers and the flag constant). Probable cause: Myers finds a shortest edit script but doesn't prefer mapping whole repeated blocks in order; slot-only differences break exact matches so a one-copy shift costs the same.
- Proposal: a second pass matching lines after normalising registers and `[esp+N]` when a `code` hunk is mostly one-sided, or re-align two one-sided hunks of similar length (58/65) against each other; optionally `dcp diffclass --pair 0xA,0xB` to check two hunks. Until then escalation reasons must explain the artefact by hand.
- Cost: ~10 minutes verifying with GNU diff. ai_FillNearRing escalated to deep at 526 differing.
